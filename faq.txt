🗂 .git history not found re: tasks — deep dive

This is the most-reported error right now. Local checks pass (git status, git log, git rev-parse HEAD all return real data) but the platform still rejects. Eng is aware. Causes ranked by frequency:

	Cause
	Fix

1
	.dockerignore excludes .git/
	Remove the line. Rezip. Resubmit. Also check .gitignore and any other ignore file the pipeline reads. #1 cause by a wide margin.

2
	ZIP layout wrong
	See expected structure below. Double-wrapped zips or flat zips break the skeleton generator.

3
	Default branch is master
	Rename: git branch -m master main. Rezip.

4
	History is "thin" / atypical
	All commits in one short burst, fresh git init, squashed-to-one, or recent rebase that orphaned reachable history. Platform wants real sustained dev activity.

5
	Hidden or stripped .git
	Some OS zip utilities strip dotfiles by default. Extract your own zip into a clean folder; confirm .git/HEAD exists before uploading.


Expected ZIP structure:

repo-name.zip
  └── repo-name/
      ├── .git/
      ├── app/
      ├── tests/
      └── ...

Debug trick: 

Add a debug command in your Dockerfile (e.g., RUN ls -la /app/<repo-name>) and submit. The build will fail but the kaniko logs will show the actual file structure inside the image — adjust paths accordingly.
If all five are clean and it still fails, post in the help thread with the repo name and a screenshot of ls -la of the extracted zip showing .git/ at the top level.

Easiness probe


Trivial fixes (one-line changes, find-replace, obvious bugfixes) get filtered. The model should need to read multiple files, reason about existing structure, and make a non-obvious change.

Difficulty unverifiable (0/10 runs solved)



Task is unverifiable: 0/10 runs solved (threshold: >=1/10). Either the task is unsolvable as specified, or the test harness has a bug preventing any agent from passing.

Acceptable range is 1–4 out of 10.
Common fixes:

* Add one hint at a time to instruction.md until pass rate enters range
* Confirm solve.sh reads the tests correctly
* Confirm the patch is actually readable by the model

Difficulty too easy (5+/10)


Make the task harder — usually by removing scaffolding hints from instruction.md, or by requiring the agent to touch more files / reason across modules.

"No trajectory in job archive" / grey chiplets


Platform-side trajectory logging glitch.

* Re-run the task
* If 5 reruns still produce no trajectories, screenshot all 5 and flag in the help thread
* Tasks with grey chiplets get rerun for delayed approval, not rejected

Why it matters: the client's pipeline (MDPT — Markov Decision Process Tuple — or POSG — Partial Observation Stochastic Game) needs clean trajectories. Until trajectories are clean, the task can't be approved.

🧪 test_patch deep dive

Error: tests/config.json: test_patch only adds 0 test(s); at least N required.

The harness reads the diff between your base commit and your task's test_patch, not your repo's existing test suite. The error means it can't see new test functions in your patch.

	Cause
	Fix

1
	Test files / functions don't start with test_
	Pytest discovery requires it. Rename.

2
	Missing __init__.py in tests/
	Add it. Some pytest configs skip directories without it.

3
	Templated from another task → empty diff vs. base
	Run git diff <base_commit> -- tests/ locally. If empty, your test_patch is empty.

4
	Used the in-website editor
	Use the import function instead. The in-website editor sometimes flattens or strips the patch.

5
	Wrong working directory in test command
	Pytest runs from a path that doesn't contain the tests.

6
	Syntax error in the test file
	File fails to load; harness reads it as zero tests.

7
	Non-Python language (Rust, Go, C, etc.)
	Confirm Dockerfile installs the language toolchain (rustc/cargo, go, etc.). Confirm test files match that ecosystem's discovery rules (#[test] in Rust, Test* in Go, _test.cc in C++). Confirm language is selected correctly on upload.


Quickest debug: apply your test_patch locally and run:

git diff <base_commit> -- tests/

What that diff shows is exactly what the platform sees.

The mechanism (credit: @Sandu Corobcenco ): the test harness expects /logs/verifier/reward.txt to exist by the time the verifier reads it. Two common causes:
Cause A: Dockerfile didn't initialize the reward file at build time
Add to environment/Dockerfile:

ENTRYPOINT []
USER root
RUN mkdir -p /logs/verifier \
  && echo 0 > /logs/verifier/reward.txt \
  && chmod -R 0777 /logs


Then in tests/test.sh, write reward 0 immediately at the top — before set -e, mktemp, patching, Node/Python, npm, etc.:sh

LOG_ROOT=/logs/verifier
mkdir -p "$LOG_ROOT" 2>/dev/null || true
(printf '%s\n' 0 > "$LOG_ROOT/reward.txt") 2>/dev/null || true

set -eu

write_reward() {
  (printf '%s\n' "$1" > "$LOG_ROOT/reward.txt") 2>/dev/null || true
}

cleanup_and_reward() {
  exit_code=$?
  mkdir -p "$LOG_ROOT" 2>/dev/null || true
  if [ "$exit_code" -eq 0 ]; then
    write_reward 1
  else
    write_reward 0
  fi
  exit "$exit_code"
}
trap cleanup_and_reward EXIT

Cause B: base image has .git history stripped
For Harbor specifically, the base image build process needs the real .git directory. If .git ended up in .dockerignore:

1. before_repo_set_cmd git operations fail silently
2. The test never runs
3. No reward file ever gets written
4. Verifier crashes with RewardFileNotFoundError

Also check that before_repo_set_cmd actually succeeds — if the patch command fails (common triggers: malformed test_patch, missing trailing newline, missing files to unlink), the rest of the pipeline silently doesn't run.
Quickest diagnostic

* Pull the Harbor base image locally
*  docker run it
*  Check /logs/verifier/reward.txt exists
* Check cd /app && git log -1 works

If either of the last two checks fails, you've found the cause.

RuntimeError: 1 / Trials: 0 / NonZeroAgentExitCodeError

No
	Cause
	Fix

1
	Base image declares VOLUME on the repo path — VOLUME /app/<repo> wipes everything written to that path in subsequent RUN layers. Kaniko log shows a git reset --hard succeed, then the next cp -a reports "Stashed 0 files." At container start, repo dir is empty (no .git, no source). Pytest fails with ModuleNotFoundError before verifier ever runs.
	Base-image side: declare the repo at a non-VOLUME path, or remove the VOLUME directive. Workaround: cp -a the repo to a non-VOLUME location in your Dockerfile.

2
	Healthcheck inherited from base image — streamlit and similar ship a healthcheck that fails in the test container. Per-trial runtime jumps from ~70s to ~140s; Harbor times out.
	Add HEALTHCHECK NONE to your Dockerfile.

3
	git not installed in base image — kaniko fails with /bin/sh: 1: git: not found on any RUN git ....
	Add apt-get update && apt-get install -y git early in your Dockerfile.

4
	solve.sh doesn't write the reward file.
	See RewardFileNotFoundError.

5
	before_repo_set_cmd raises on a non-fatal warning. Wrappers treat warnings (e.g., git clean -fd "Refusing to remove current working directory") as fatal RuntimeError.
	Avoid commands that warn-but-succeed in setup hooks.

6
	Auto-injected test_patch layer collides with your test.sh. Silver appends a git apply --verbose - layer for test_patch during build; if test.sh also applies the same patch at runtime, the second apply fails.
	Don't re-apply test_patch in test.sh.



ModuleNotFoundError: No module named 'app' (or similar)

Pytest can't resolve your package. Three options:

* Add conftest.py at repo root
* Install the package in your Dockerfile: pip install -e .
* Set PYTHONPATH in the test command

Rejections by class — feedback + explanation

Issue
	feedback_given
	explanation

Q1 solution-inject 
	"Heads up - the grader is basically doing the agent's work for it here. The verifier applies your gold solution itself (something like bash /solution/solve.sh or an apply_reference_patch call) before it scores anything, so a "pass" doesn't actually mean the agent solved the task. Could you pull that solution-applying step out of the verifier and have it grade only the agent's own changes against your FAIL_TO_PASS / PASS_TO_PASS tests? Worth double-checking too that /solution and the reference patch aren't reachable while the agent is running."
	The test harness quietly pastes in the correct answer before it grades. So every run "passes" no matter what the agent did — the score measures the answer key, not the agent. The fix is to delete that paste-in step and grade only what the agent actually wrote, and to lock the answer file away so the agent can't peek at it either.

Q1 oracle-gate (7 tasks)
	"The reward here keys off an oracle/marker (something like is_oracle_trial writing reward.txt) instead of the actual test results, so the pass/fail isn't really tied to the agent's code. Mind dropping that marker branch so the verdict comes straight from the tests? And make sure the oracle markers can't be reached or faked during the graded run."
	Instead of deciding pass/fail from the tests, the grader looks at a little flag file and trusts it. That means the verdict can be set by something other than the agent's work — it can even be faked. The fix is to throw away the flag-file shortcut, let the test results decide directly, and make sure nothing can flip that flag during a real graded run.

F2P/P2P FAIL (4 tasks)
	"When we run your base repo + gold tests, then layer on your gold solution, the FAIL_TO_PASS tests don't actually flip from failing to passing - so the solution and the tests aren't quite lining up. Could you get the gold solution to make those tests pass (or fix the test/config), then give it another run to confirm?"
	The task promises certain tests should start failing and then pass once the right fix is applied. But when we apply the official fix, those tests still don't pass — so the answer and the tests don't match up. The fix is to get the official solution to actually make those tests pass (or correct the tests/config), then re-run to confirm it lines up.

* Look through your own code — typos, paths, naming conventions
* Test locally — reproduce the failure before flagging
* Send concrete context — screenshots, error logs, what you've already tried
* Check this FAQ and the pinned threads first
* Check that your question isn't already answered in the active help thread

Debugging is part of software engineering. We can only help with platform-side issues — work-side issues are yours to chase down. Reasoning through your error logs solves the majority of what gets posted.
